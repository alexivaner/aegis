# Aegis — Local or cloud?

Independent experimental project using fictional notes and publicly available technologies. The main case study is a preset-based routing lab. Choose a scenario, see local/cloud/blocked, then change one condition. The meeting and notification implementations remain as source references and regression tests.

## Run locally

From the standalone Aegis repository root:

```sh
uv sync --project ai-runtime
npm run aegis:validate
npm run aegis:export
npm run runtime
# second terminal
npm run dev
```

Open `/#routing-lab` (or `/work/aegis/#routing-lab` when embedded in the portfolio). The unauthenticated API binds only to `127.0.0.1:8011`; Astro's development proxy forwards `/api/aegis`. It is not a public production service.

## Primary scenario lab

`RoutingLab.astro` calls `POST /api/aegis/route` with fictional conditions. The actual Python policy filters candidates, then the scheduler selects among the admitted candidates, applying the selected local/cloud preference (local by default) only among admitted candidates. No model executes and no document is sent. The execution-backend role is a preview of the next boundary, not an execution claim.

The six presets are generated by `export_demo.py`. Without the local API the browser shows those recorded Python results and disables custom edits. The live API accepts arbitrary validated conditions; the browser only formats the result. Preset selection and input changes use a generation guard to avoid showing an old request as the current decision.

All eleven controls are visible in four labeled groups: telemetry (memory, battery, CPU, online/unstable/offline network), policy (cloud permission, basic/reasoning task, wait budget), scheduler (local/cloud preference), and execution-backend profiles (local/cloud availability and local reasoning capability). Every change updates all four input/output step cards beside the decision. Selecting a step highlights its controls. Telemetry remains simulated, policy and placement execute in Python, and execution is explicitly a preview. The preference cannot override policy admission. The example local profile needs 4 GB and estimates 1200 ms; the cloud profile estimates 1600 ms. Thresholds are reference assumptions, not hardware measurements or model-performance claims.

Architecture, testing and engineering decisions are collapsed by default so the first experience stays focused. The sections below document the retained meeting runtime, which is no longer the primary UI.

## What runs for real

| Responsibility | Implementation | Limit |
| --- | --- | --- |
| Telemetry | Supplied DeviceContext plus SystemClock and measured Python elapsed work | Resource inputs are simulated. Untimed snapshots claim no separate timing. No GPU/NPU, thermals or energy counters. |
| Policy engine | Shared PolicyEngine / RuleBasedPolicyEngine admits candidates using privacy, network, capabilities and resource estimates | Profiles are explicit assumptions, not optimal scheduling or hard deadlines. |
| Scheduler | WorkloadScheduler chooses an admitted backend; CooperativeQueue orders interactive and background work | One cooperative worker; no hardware preemption or distributed queue. |
| Execution backend | MeetingInferenceProvider: extractive learning rules or configured actual model adapters | Learning profiles never invoke a model or network. Actual model quality is unevaluated. |

The meeting service composes these boundaries and produces a bounded sequence of trace snapshots. Domain parsing, validation and queue rules import no framework, database or model SDK. HTTP is an incoming adapter; composition selects concrete implementations. Runtime calls can move outward while source dependencies point toward application-owned contracts.

## Learning mode

Local/cloud candidates are fictional model profiles: local needs 4 GB and has an 800 ms latency estimate; cloud has a 1200 ms estimate. Both implement the same local extractive rules. The cloud learning path is a simulation, with no external request. Output is labeled as text extraction, not LLM reasoning or generated abstractive summarization.

The extractor selects the first three source contributions as key points, recognizes explicit named-speaker “I'll / I will … [by …]” commitments, and identifies “we agreed / we decided” passages. Missing metadata remains null. Unsupported wording can produce no action; it is not guessed. These limitations are deliberate and visible.

Private notes forbid cloud even when local execution is impossible. Offline conditions forbid cloud. No permitted candidate means blocked execution with no fabricated document. Busy-device input changes the fictional CPU/memory snapshot; it does not create actual system load.

## Actual model integration

Use an already installed, running Ollama model:

```sh
AEGIS_OLLAMA_MODEL=your-installed-model npm run runtime
```

No model download occurs. The adapter uses the loopback `/api/chat` endpoint, meeting JSON schema, temperature zero and a 900-token cap. CPU/GPU execution depends on Ollama/model compatibility; Aegis does not directly select an execution provider. The initial local memory/latency profile is an estimate needing calibration.

Cloud is opt-in through `AEGIS_ENABLE_CLOUD=1`, `AEGIS_CLOUD_MODEL`, `AEGIS_CLOUD_API_KEY`, and optional `AEGIS_CLOUD_ENDPOINT` (HTTPS). Actual model mode must be selected, and the current request must explicitly permit cloud processing by disabling the on-device-only restriction. Keys stay in the server environment. Never use company credentials or confidential notes for this independent demo.

Primary transient failures get at most two attempts with 20 ms backoff; invalid output skips retry. Only already-admitted alternative providers may be tried. Each call has an 8-second timeout, with at most two configured candidates. Explicit fault injection replaces the first provider call with a test fault. Failure of every permitted candidate produces a visible failed result; model mode does not silently substitute a successful rules result.

No actual LLM execution is claimed by recorded fixtures or evaluation. Contract tests intercept HTTP. Real models can be slow, unsupported or inaccurate; the timeout/token/resource settings need actual evaluation.

## Evidence and review

Input is bounded to 6000 characters, 20 nonempty lines, 800 characters per line. Every output item must have known source IDs and an exact quote from a referenced contribution. Owners/due fields must occur as word-bounded phrases in a cited speaker/text; missing values remain null. Unknown fields/tools/actions are rejected. A model cannot execute arbitrary tools or external actions.

Literal references do **not** prove semantic entailment of a model paraphrase. The UI shows the source beside the output and encourages review. Learning output is extractive; actual model output requires human verification. No external task, email or notification is created.

## Work queue

A workspace retains at most 12 jobs and 12 recent queue events. One worker advances one unit at a time. A meeting job is one bounded workflow; reference indexing is four real Python token-indexing chunks over fictional text. Work advances only through run/step requests. There is no continuous background activity.

Interactive jobs have base priority 0, background jobs 10. Each waiting turn improves effective priority by 2; ties preserve insertion order. A continuously waiting background job receives a turn after at most five higher-priority selections in this fixed-priority reference case. This is turn-based aging, not a wall-clock deadline promise. Work yields between chunks; an active HTTP inference call cannot be interrupted by the queue. Queued work can be cancelled before its next turn.

The worker lock serializes execution in this single process. There are at most 16 workspaces; inactive ones expire after 30 minutes, and capacity may evict the least recently used workspace. Sessions and result evidence are in memory, not durable or authenticated. Editable notes stay out of trace snapshots/access logs and generated source/fixtures, but remain in bounded result memory for review until expiry/eviction/restart. Public deployment requires authentication, ownership enforcement, retention controls and a durable design.

## Offline and testing

The exporter executes three fictional meetings across six experiments and saves the actual outcomes, queues and traces. When the API is absent, arbitrary editing/conditions/queue execution are disabled; visitors inspect these recorded cases. There is no duplicate JavaScript policy.

`npm run aegis:validate` runs pytest with JUnit, Ruff and strict mypy. `npm run aegis:export` consumes the real report and runs the experiments. The archive includes independent Python sources, tests, lockfile and docs. The small dataset demonstrates behavior, not model accuracy or production performance. The retained notification tests/evaluation are identified separately in the report.

Next work: human-labeled evaluation of real models, semantic support checks, calibrated hardware/resource profiles, durable checkpointed queues, authenticated sessions and stable feedback control. Automatic hysteresis/cooldown adjustment is not implemented.
